STUDYSHIT • INCREMENTAL HTML PIPELINE • SHARED RULES

GOAL: An MA International Business and Finance student (THA Augsburg, Germany) wants to KNOW the lecture and pass the exam without wading through theory. Build notes that are short, accurate, complete and genuinely enjoyable to work through: a hook, a clear idea, a worked example, something to see, something to try, a question to test yourself. Everything the lecture taught is covered; nothing beyond it is padded in. Correct at master's level, never a research text. If a sentence does not help the student understand or answer an exam question, cut it.

THREE NON-NEGOTIABLES:
1. COMPLETE: every concept, formula, number, lecturer example and warning from the sources appears somewhere (tracked by source IDs).
2. ACCURATE: every number in text, examples, visuals, calculators and answers is recalculated and correct; lecturer errors get a short "Fact check".
3. LESS: the shortest version that still teaches it. Show and let the student try rather than explain at length.

LEARNING FORMAT (every stage follows this; it overrides any wording elsewhere that asks for more depth):
Each topic is one <section id="topic-tNN" data-format="compact-v2"> built from these parts, in this order:
1. Plain title that says what the student can do (for example "Pricing a bond from its cash flows").
2. Hook (class "hook"): ONE short line that makes the student curious: a concrete question, a surprising fact from the lecture, or a decision ("Would you pay 125 for a bond that pays you 125 in total? You shouldn't.").
3. Concept blocks (h3), 1-4 per topic. Each block:
   - the idea in plain words, max ~80 words. Define a term only where it first appears, in one short clause or sentence, in bold. No separate definitions lists, no definitions of words the lecture does not use;
   - the lecture's formula if there is one, then each symbol in a few words (no derivation unless the lecturer derived it);
   - a worked example (class "example") using the lecturer's numbers where possible, shown as numbered steps revealed one at a time (see INTERACTIVE PARTS); invented numbers are labelled ILLUSTRATIVE;
   - a visual (class "visual") whenever the idea involves numbers, time, a process or a relationship;
   - one quick check (class "quick-check") as an instant-feedback question (see INTERACTIVE PARTS).
4. "Try it" (class "try-it", optional, max 1 per topic): a small calculator or slider for a formula worth playing with (for example change the yield and watch the bond price move). Only where playing with it builds intuition.
5. Remember (class "takeaways"): 3-4 one-line bullets, including the most common mistake ("Watch out: ...").
6. Practice (added in S05, class "practice").

LIMITS:
- Prose per topic: target 200-450 words, hard cap 550. Formulas, tables, visuals, example steps, interactive parts and questions do NOT count, so they are never squeezed; prose is.
- Visuals: at least one per topic whenever the topic has numbers, time, a process or a relationship; at most 3 per topic. Small inline SVG or HTML tables (no external images, no stock art, no decoration), computed from the stated numbers, labelled axes and units, one-line caption. Keep each SVG roughly under 4 KB.
- Real-world example (optional, class "real-world"): at most one per topic, max ~60 words, with an inspected citation, or labelled ILLUSTRATIVE.
- Slide pictures: describe only exam-relevant content, in at most 2 sentences; ignore decorative images. Redraw an important chart instead of describing it.
- Lecturer errors: keep the statement and add a 1-2 sentence "Fact check" (class "fact-check").
- Tone: direct, friendly, confident; short sentences; one idea per paragraph; no filler, no repetition across topics (link back instead), no childish jokes.
- Topics without data-format="compact-v2" are in an older format. When their stage processes them, rewrite them into this format from their existing content and sources, keeping every lecturer fact, number, formula and source ID; cut only explanation.

INTERACTIVE PARTS (vanilla JavaScript, no libraries, no network requests; the page must still be fully usable without JavaScript):
- One shared script at the end of the page, <script id="study-js">, kept under ~8 KB, provides: step-by-step reveal for examples (button "Next step", all steps visible without JS), instant-feedback questions, flashcards, and a progress bar. Add it the first time a stage needs it; extend it, never duplicate it.
- Instant-feedback question markup: a container with data-quiz, options as buttons with data-correct="true" on the right one, and a short "why" explanation shown after any click (right: green + why; wrong: red + why + the right answer). Numeric questions use data-answer="112.11" and data-tolerance="0.01" with an input and a Check button. Always include a <details> fallback with the answer for no-JS and print.
- "Try it" calculators: inputs and output inside their own container, driven by a small inline script (max ~40 lines) that only touches that container. Its default inputs MUST be the lecturer's example and its default output MUST equal the example's printed result (state both in the build log).
- Progress: each topic ends with a "Got it" checkbox; the shared script stores it in localStorage (wrapped in try/catch) and updates a progress bar at the top. Without storage it simply does not persist.
- Print CSS shows every answer and every example step and hides buttons.

PAGE DESIGN: One inline stylesheet styling these classes once, simply and attractively (light tinted cards, clear headings, readable on mobile, good contrast, print-friendly): hook, example, visual, quick-check, try-it, takeaways, fact-check, real-world, practice, cheat-sheet, flashcard, progress. Add missing styles the first time a stage needs them; do not restyle the whole page.

ONE FILE: Each lecture has ONE evolving HTML document at subjects/<subject-slug>/lectures/<lecture-slug>/study.html. Edit it incrementally, never regenerate from scratch. Maintain the source ledger with L001... identifiers, stable topic-t01... IDs, data-source-ids, and a collapsed build log. Keep all unique taught information.

SOURCE FIDELITY: With recordings, transcript establishes what teacher taught; class slides clarify formulas/visuals. Without recording, class slides ARE primary lecture content; never invent teacher speech. Module-wide materials help but are not automatically lecture coverage. Inspect slides visually; report unavailable visuals. Distinguish teacher statements, AI explanations, illustrative numbers, and verified outside facts.

RESEARCH: External company facts, figures, dates, standards, laws, and attributed definitions require actually inspected citations next to the claims; never fabricate sources. Unverified additions must be omitted or labelled uncertain, not asserted. Illustrative arithmetic must be checked. Preserve disputed lecturer statements with a separate correction, not silent alteration.

PERSISTENCE CONTRACT (CRITICAL):
- Read latest study.html and state.json from creativeidiot123/studyshit before editing an existing lecture. Derive paths from established state, never guess an existing path.
- Under the same lecture folder, maintain inputs/source-manifest.json with original filenames, source types, file sizes when known, and ChatGPT attachment provenance. The studyshit repository is PUBLIC. Do not upload original copyrighted PPT/PDF/transcript bytes, personal student details, or confidential source documents to this public repository by default. Only copy originals under inputs/ when destination access/privacy and permission to share are confirmed and a binary-safe upload succeeds. Never imply a chat attachment was copied to GitHub unless the transfer was verified.
- Write changed study.html to GitHub, using the current blob SHA for updates. For new lectures create the file. Confirm the new content by re-fetching it. Update state.json after the HTML write, then verify state as well. Use connector writes or another explicitly verified authenticated method. A sandbox link, inline HTML, or a claimed save is NOT a GitHub commit.
- Batch sizes: S03 one topic per run, S04 up to 4 topics per run, S05 up to 3 topics per run. The source manifest is metadata; it is NOT a substitute for reading the actual uploaded PPT or its rendered slide images. Update topic data-progress and state.json. With incomplete work, keep the current stage and use STEP_MORE.
- If GitHub write/read, source access, identity, credentials or needed human decision is blocked, state the exact issue and end WAIT_FOR_HUMAN. NEVER claim a stage succeeded without a verified persisted HTML version.
- Maintain state.json keys: schema_version=1, subject, lecture, html_path, stage, completed_topics (object mapping stage numbers to topic IDs), next_topic, source_complete, issues, updated_at. Stage is the latest fully completed stage number (0-7). Keep JSON valid.
- Preserve original HTML IDs, source mapping, sections, figures, equations, practice answers, and already verified facts. Use targeted edits. Check that unrelated sections survive.
- If other information is unavailable, do the most verifiable work possible but DO NOT falsely signal success.

VERIFICATION GATE: A stage's STEP_DONE is only a claim, NOT permission to execute the next stage. Tampermonkey v1.3.37+ must queue /prompts/08-verify-stage.txt to independently verify the just-completed stage against actual saved GitHub content and source material. A VERIFY_PASS moves to the next stage; VERIFY_FAIL returns to the same stage for local repairs. Three verification failures for one stage stop automation for human review. S07 FINAL_READY also requires its own independent verifier PASS. When a user prompt starts [STUDYSHIT AUTO VERIFY Sxx], execute the read-only verifier only. When it starts [STUDYSHIT AUTO REPAIR Sxx], fix the previous verifier's specific findings even if state.stage already equals the stage number; do not advance without a new successful verification. The verifier cannot fix source material, only report PASS/FAIL or WAIT.

TERMINAL TOKENS: Every finished response must end with exactly ONE marker on the final standalone line. No text after it, and no code fence or quotation around it.
[[STUDY_STEP_MORE:S01]] ... [[STUDY_STEP_MORE:S07]] = valid committed progress within the same stage; userscript re-runs that stage WITHOUT a verifier.
[[STUDY_STEP_DONE:S01]] ... [[STUDY_STEP_DONE:S06]] = claimed complete stage is saved; userscript schedules one independent VERIFY turn for that stage, NOT the next stage.
[[STUDY_FINAL_READY]] = claimed completed stage 07 is persisted, but must still be independently verified before final acceptance.
[[STUDY_WAIT_FOR_HUMAN]] = human action required; automation must not advance. Explain blocker before marker.
[[STUDY_VERIFY_PASS:S01]] ... [[STUDY_VERIFY_PASS:S07]] = ONLY a read-only verification turn can approve a matching stage. S07 PASS is the final accepted completion.
[[STUDY_VERIFY_FAIL:S01]] ... [[STUDY_VERIFY_FAIL:S07]] = ONLY a read-only verification turn can return repair findings and re-run the SAME stage.
Use only the marker for the stage actually executing. A verifier must NOT output normal STEP_DONE/STEP_MORE/FINAL_READY. Never emit CGR_DONE together with a STUDY marker; existing resilience layer recognizes STUDY markers natively. [[CGR_HIBERNATE_GITHUB_10M]] is reserved for already-running GitHub Actions whose completion must be checked later, not ordinary task progress.
Do not include terminal tokens in student-facing HTML or in ordinary prose except protocol documentation.
